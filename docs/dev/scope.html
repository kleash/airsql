AirSQL 1.0 Scope

A native Mac client for MariaDB and MySQL. This page lists every HeidiSQL feature, plus the DataGrip features and the AirSQL-only features asked for. The releases shown are the decided scope of 2 November 2026. Changing a row marks it as changed; copy the list to pass changes on.

Where the scope stands

Effort: S is up to 2 days, M is about a week, L is 2 weeks or more, for one developer working with agents. The weeks figure adds up the 1.0 rows (S = 0.3, M = 1, L = 2.5) and is a rough guide only. Parallel agent lanes, as used for AirSCP, shorten the calendar time.

Decisions to settle before building

How AirSQL talks to the database

Choose between bundling MariaDB Connector/C (libmariadb, the library HeidiSQL itself uses) and writing the MySQL wire protocol in Swift.

Suggested: libmariadb, built by a pinned, checksummed script the way AirSCP builds FreeRDP, and linked against the OpenSSL that script already builds. It handles caching_sha2_password (MySQL 8 and 9), MariaDB ed25519, TLS, compression and multiple result sets. It is LGPL-2.1, so ship it as a dylib inside the app. A Swift protocol would need its own ed25519 code (CryptoKit only takes 32-byte seeds, and MariaDB hashes the password itself) and adds weeks of work. The mysql-nio package in the MySQLClient folder fails on caching_sha2_password and would break AirSCP's rule of no third-party Swift packages.

Every route ends in a local endpoint

Built as a private Unix socket (plan R1), not a 127.0.0.1 port, so no other local user or process can use the tunnel.

SSH routes forward with ssh -L 127.0.0.1:<port>:db:3306 on AirSCP's ControlMaster session. Proxy-only routes get a small relay inside the app that listens on 127.0.0.1 and connects through SOCKS5 or HTTP CONNECT.

Why it matters: the driver, mysqldump, mysql and "Open in Terminal" all connect to the same 127.0.0.1 port. The client tools then work over every route without any proxy support of their own. AirSCP's Session, Askpass and ProxyConnect code does most of the SSH part already, and both apps are Apache 2.0 under the same author.

What agents may do

The request is for agents to read schema, write complex SQL and test it in the AirSQL console, where you can see and edit it.

Decided for 1.0: agents read schema, run read-only queries, place SQL in a console tab, and drive the whole UI as they do in AirSCP. A separate agent-write tool is skipped. Driving the UI means an agent could press Run, Apply or Drop, so 1.0 keeps AirSCP's "Ask before agents change things" setting, on by default: anything that changes data or structure waits for your OK. Read-only queries are checked twice: only SELECT, SHOW, EXPLAIN, DESCRIBE and WITH are accepted, on a session set to SET SESSION TRANSACTION READ ONLY. A read-only database user is the hard guarantee.

A separate app, built like AirSCP

Same toolchain: Swift 5 language mode, AppKit with SwiftUI, macOS 13.1 or later, Command Line Tools only, no third-party Swift packages, tooltips on every control, signed and notarized, Homebrew cask.

Note: HeidiSQL 12.x now ships a native macOS build (Apple silicon only). AirSQL stands out through its Mac-native UI, its SSH, jump host and proxy routes, its agent support, and builds for both Intel and Apple silicon. The MySQLClient attempt was dropped because it felt slow and lacked basics such as right-click menus, double-click to edit, multi-select and shortcuts. Those basics are now 1.0 rows with performance targets, in the first table below.

The data grid is built natively

No capable macOS grid library exists: the known Swift grids (SpreadsheetView, SwiftDataTables) are iOS only, and Mac database apps all build their own. NSTableView selects whole rows and slows down on wide tables, and MySQLClient used it and still felt laggy.

Decided: one custom grid view that draws only the visible cells, reused for table data, query results, Transpose and recon diffs. Rows stream in batches into a page cache off the main thread, and each cell's text is computed only when it scrolls into view. A single text field sits over the cell being edited. The grid exposes its visible cells to accessibility, for VoiceOver and for agents. First, a 3-day spike with pass marks: 1,000,000 rows × 50 columns and a 300-column table scroll at 120 Hz without dropped frames; ⌘/⇧ block selection, arrow and Tab moves, Return to edit, copy as TSV; Transpose switches instantly; VoiceOver reads the cells. Fall back to NSTableView only if the spike misses those marks.

Connections · from DataGrip

SSH, jump host and proxy routes

  • SSH with a password, a key, ssh-agent or 2FA prompts. Your ~/.ssh/config aliases work.
  • One or more jump hosts (ProxyJump), each with its own login.
  • SSH through an HTTP or SOCKS5 proxy, using AirSCP's ProxyCommand helper.
  • Proxy only: the database through SOCKS5 or HTTP CONNECT, with no SSH.
  • Host key trust sheet, reconnect after sleep, and a log of every command AirSQL runs.
  • Later: pick a host already saved in AirSCP as the SSH route.
AI agents · like AirSCP

MCP for Claude Code and Gemini CLI

  • claude mcp add airsql -- /Applications/AirSQL.app/Contents/MacOS/AirSQL --mcp, and the same command with gemini mcp add. A Claude Code plugin as well.
  • Tools: list_connections, list_databases, describe_table (columns, indexes, foreign keys, DDL), get_schema (a compact dump of a whole database), search_schema.
  • run_query: read-only, capped at a row limit. Results also appear in an Agent tab that you can watch.
  • open_in_console: puts SQL in a console tab for you to edit and run. read_console gives the agent what you ran and the result or error.
  • Off until you turn it on. Access is set per connection (Off, Schema, or Schema + read). Agents never see passwords, and sample rows are off by default.
Client tools · your binaries

Point to mysql / mariadb tools for dump and restore

  • Settings ▸ Client tools: paths to mysql or mariadb, and to mysqldump or mariadb-dump. AirSQL finds them in Homebrew, /usr/local/mysql/bin, MAMP and PATH, and shows each version.
  • Override them per connection: MariaDB tools for MariaDB servers, MySQL 8 tools for MySQL 8. AirSQL warns about mismatches and adds --column-statistics=0 when it is needed.
  • Export: pick databases and tables; structure, data or both; routines, events and triggers; single transaction; gzip; extra options. Shows the full command line, progress and Cancel.
  • Restore a .sql or .sql.gz file into a chosen database. The file goes through the app, so progress is real. Choose to stop at the first error or continue.
  • Passwords go in a temporary 0600 defaults file, never on the command line.
Data grid · the heart of the app

Understand, filter, search and edit any table

  • Understand: typed headers with key marks, selection totals in the status bar, a column summary from the server, and a value panel with a JSON tree, hex and images.
  • Filter and sort on the server (every row) or locally (loaded rows only). The bar always says which one is active.
  • Search all columns in one box, as in HeidiSQL, on the server or in the loaded rows, with matches highlighted.
  • Edit by type: date and timestamp pickers with the time zone shown, a JSON editor that checks before Apply, ENUM pick-lists, BIT checkboxes, a hex editor for BLOBs.
  • Auto-generated values are handled for you: AUTO_INCREMENT, DEFAULT and generated columns stay out of the INSERT, and the real values show after Apply.
  • Fast at a million rows; right-click, double-click, ⌘/⇧ multi-select and the keyboard work everywhere.

Look and feel (from the DataGrip and HeidiSQL research)

A layout you already know

Connections and the navigator on the left, query and table tabs in the middle, results under the query. The tab toolbar holds Run, Explain, History, the transaction mode with Commit and Rollback, Cancel, and the database switcher. A connection's colour tints its tree, tabs and toolbar, so production always looks like production.

Fewer concepts than DataGrip

One kind of query tab: bound to one connection, saved as a .sql file or kept unsaved and restored after relaunch. ⌘↩ runs the statement under the cursor and briefly highlights it, with no chooser popup; ⇧⌘↩ runs everything. Result tabs are reused unless pinned and are named from the comment above the query.

Nothing changes by surprise

Grid edits wait for Apply and run in one transaction. An open transaction shows a badge, and closing a tab with uncommitted work asks first. On production connections the SQL preview is always shown first, and read-only is enforced by AirSQL itself.

Light where DataGrip is heavy

Published targets: launch under 1 second, idle memory under 150 MB, the grid targets in grid-spec.md. Every schema shows by default, metadata comes from information_schema and is cached, and only what a DDL statement changed is refreshed.

The full merged grid spec, with every HeidiSQL and DataGrip grid feature and the Mac shortcut map, is in grid-spec.md, the plan in plan.md and the screens in mockups.html, all next to this page. The research notes are in research.md.

Suggested build order for 1.0

  1. Connect. libmariadb build script, saved connections in the Keychain, all five routes ending in a private socket, TLS, navigator tree, process list. Ends with: browse any server you can reach today.
  2. Grid spike (3 days), then feel first. Grid, tree and editor built with right-click, double-click, multi-select, shortcuts and the performance test from the first commit. Adding these later is the trap MySQLClient fell into.
  3. Console. Editor with highlighting and completion from cached schema, run and cancel, result tabs, history, SQL log, auto-commit with Commit and Rollback, safety prompts.
  4. Agents. --mcp server, schema tools, read-only run_query, open_in_console, activity list; then UI driving (snapshot, menu, press) behind the ask-first gate. This comes early because it reuses the schema cache and the console, and it is AirSQL's main difference from HeidiSQL.
  5. Data and structure. Grid editing with pending changes, value viewers, copy and export; table editor with columns, indexes and foreign keys; DDL editing for views and routines.
  6. Client tools and data transfer. Settings ▸ Client tools, Export and Restore sheets, Open in Terminal; built-in SQL export, copy to another server, CSV import, running a .sql file.
  7. Compare and reconcile. Structure diff first (it reuses the schema cache and DDL code), then data diff with server-side chunk checksums, then the sync script.
  8. Liquibase. Changelog from a schema (DDL, DML, both), and Save as Changeset on every change sheet. This reuses the SQL the table editor and grid already show.
  9. Power features. Maintenance, bulk table editor, find text on server, EXPLAIN plan, query profile, reformat, ER diagram.
  10. Ship. Tooltips on every control, docs site, agent guide, signing, notarization, Homebrew cask.
